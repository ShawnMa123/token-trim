# 安全模型

## 边界

`rtk-go` 是**输出后处理器**，不是权限边界，也不是 Codex sandbox 的替代品：

- 它不提升、不绕过、不重试 Codex 的权限决策；
- 它不自动改写命令；默认只处理用户显式传入的 argv；
- 它不读取凭证、不访问网络、不调用模型 API；
- 它只在本地处理子进程已经产生的 stdout/stderr。

如果包装器绕过了宿主拒绝，这是安全缺陷，不是可接受的性能优化。

## 原文存储

有损过滤前必须完整保存原文。存储安全要求：

- 目录是用户私有目录，拒绝 symlink/junction 作为数据根；
- Unix 使用 `0700` 目录和 `0600` 文件，无视宽松 umask；
- Windows 使用受保护 DACL，仅当前用户、SYSTEM、Administrators；
- 写入使用临时文件 + 原子 rename，避免半成品；
- 配额/保留期清理只作用于受管目录内对象；
- 目录权限不可隔离时禁用存储，有损过滤回退原文。

`--no-store` / `RTK_GO_NO_STORE=1` 禁止落盘，同时禁止有损过滤。原文不会因为“反正可以
recall”而被写入不受信任的位置。

## 命令执行

- 原生 executable 单次 argv 执行，不经 shell 拼接；
- Windows 不隐式执行 `.cmd`/`.bat`/`.ps1`；
- stdin/stdout/stderr 原样连接；TTY 输出不做过滤；
- Unix 用进程组、Windows 用 Job Object 回收自身进程树；
- Ctrl-C/取消只影响自身树，不按名字杀进程；
- 启动失败映射 126/127，wrapper 生命周期失败用 125，子进程退出码原样透传。

## 数据泄漏面

可能进入上下文的内容：

1. 子进程输出（用户本来就会看到）；
2. `recall` 的原文（用户主动读取）；
3. 本机统计只记录计数/字节/模式，不记录完整 argv、环境、输出正文、cwd 或路径。

不会发送到任何远端。Codex 本身如何使用这些文本，取决于 Codex 的配置和网络策略。

## 过滤器的输入守卫

以下输入直接透传，不进入解析器：

- 非 UTF-8、NUL、异常控制字符；
- 未完整验证的 ANSI 序列（已完整验证的 SGR 样式会被移除）；
- TTY 输出、交互输出；
- 机器可读格式（`rg --json`/`-0`、`git --porcelain`、`go test -json` 中未知事件等）；
- 不完整捕获、原文保存失败、过滤超时、panic、字节收益不足。

## 报告安全问题

请提供：版本、OS/架构、命令、退出码、是否使用 `--no-store`/`--raw`、最小复现。
不要附真实凭证或公司敏感日志；用合成 fixture 复现即可。

## 还原数据丢失/损坏风险

### 已实现的保护

1. **先提交、后发布**：有损候选只有在 stdout/stderr 完整、manifest 写入成功、目录
   rename 成功后才输出；任一步失败都回退原文。
2. **完整性校验**：manifest 记录每路字节数和 SHA-256；`recall` 在返回任何内容前
   重新计算并比对。截断、篡改、错文件都会返回 `ErrCorrupt`，不会静默返回半份数据。
3. **原子发布**：流文件写入 `.partial-*`，逐个 `fsync`；manifest 最后写入；整个目录
   rename 到 `runs/<id>`。Unix 还会 `fsync` partial、runs 和 root 目录。
4. **过期/配额**：默认保留 24 小时、总配额 256MiB；清理只处理完整、已过期、位于
   受管根内的对象；symlink/junction 不跟随。
5. **私有权限**：Unix `0700/0600`；Windows 受保护 DACL；目录权限不合格时禁用存储，
   有损过滤回退原文。
6. **不可执行**：`recall` 只读本地文件，绝不重跑命令；ID 必须是 32 位小写 hex，
   路径做 containment 检查。

### 剩余风险

| 风险 | 影响 | 当前处理 |
|---|---|---|
| 超过保留期或 `clean --expired` | 记录被删除，`recall` 返回 `ErrExpired`/`ErrNotFound` | 用 `--raw` 自行留档；不要把 recovery 当长期归档 |
| 磁盘满、配额耗尽、锁竞争 | 无法提交/获取租约 | 有损候选回退原文；不会输出无法恢复的摘要 |
| 进程崩溃/断电 | 可能留下 `.partial-*`；Windows 目录项持久化是 best effort | Unix 已 fsync 文件和目录；partial 24h 后清理 |
| 被同用户恶意修改 | 可同时改流和 manifest 哈希，完整性校验无法防同用户伪造 | 依赖 OS 账户隔离；不要把数据根放到共享目录 |
| 明文存储 | 有权限的用户可读原文 | 用户私有 ACL；不用于保存凭证/高敏数据 |
| 时钟跳变 | 可能提前过期或延后清理 | 使用本地时钟；关键审计不要依赖恢复记录 |
| recall 与清理并发 | 读到一半目录被删 | 记录已过期时本就不可保证；先 recall 再清理 |

### 结论

正常单机、单用户、24 小时内：提交成功的有损输出有强完整性校验和原子发布，**“摘要
已输出但原文没保存”的窗口被关闭**；失败时回退原文。真正无法消除的风险是：过期删除、
磁盘/配额、同用户篡改、平台断电语义，以及明文落盘。需要“绝对可恢复”时，使用
`--raw` 或自行持久化原始输出，不要把 24 小时缓存当唯一副本。
